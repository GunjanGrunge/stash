## 1. What This Project Is

STASH is a creator-first cloud drive: a mounted drive on Windows and macOS
that preserves a creator's exact folder hierarchy, keeps payloads in the
cloud, makes assets searchable through deterministic (non-LLM) metadata, and
follows the user across devices. Product promise: *"Stash it. Find it. Use it
anywhere."* Private beta is 2 users at 1 TB each, AWS-first in `ap-south-1`.

- **Product source of truth:** `STASH_PRD_v0.1.md`
- **Current approved spec:** `_bmad-output/planning-artifacts/specs/2026-09-15-aws-control-plane-design.md`
  (AWS control-plane foundation — approved 2026-09-15)
- **Intake record:** `_bmad-output/planning-artifacts/2026-09-15-sia-intake-record.md`

Spec/plan/session artifacts live under `_bmad-output/` rather than `docs/`,
by user decision at intake, so SIA and BMAD share one artifact location.

## 2. Project-Specific Rules

These come from the PRD and the user's stated decisions. They are not
generic good practice — each one is specific to STASH and checkable.

1. **Never reorganize a user's library.** No renaming, flattening,
   categorizing, or moving of creator content, in code or in UI copy.
   `original_relative_path` is preserved verbatim. (PRD §4.1)
2. **File, Folder and Stash are three different concepts.** A Stash is
   metadata about one ingestion event; it never replaces folders. Do not
   collapse them in schema, API or copy. (PRD §4.2)
3. **A checksum match is never an identity match.** Identical content in two
   different packs stays two assets with two keys. Nothing may delete or
   repoint a user's logical path on a hash match. (PRD §4.3, §7)
4. **Never mark something Stashed that is not verified committed.** Every
   transition to `committed` is a conditional write guarded by verification
   against S3. (PRD §13)
5. **No LLM in the product runtime.** v1 uses deterministic tokenization,
   aliases, structured filters and lexical ranking. Do not introduce a model
   call into a product code path. (PRD §4.5, §14)
6. **S3 object keys are `users/<user_id>/<file_id>` — opaque IDs only.**
   Creator-supplied paths never enter a key. (Spec §3.3, §6.1)
7. **`user_id` comes only from verified JWT claims.** Never from a request
   body, query string or path parameter. (Spec §6.1)
8. **S3 versioning is off, so never overwrite an existing key.** Every Stash
   writes a new `file_id`. An overwrite is unrecoverable. (Decision 2026-09-15)
9. **Payload bytes never transit Lambda or API Gateway.** Control plane
   authorizes; the client transfers directly to S3. (PRD §11)
10. **Use STASH vocabulary in all user-facing text**: Stash it / Stashing /
    Stashed / Recent Stashes / Free up space. Do not brand generic concepts
    (Files, Folders, Search, Settings, Devices). (PRD §19)
11. **Every `cdk deploy` or mutating AWS CLI call is High severity** and
    requires explicit approval immediately before it runs. Creating billable
    cloud resources is never bundled into a larger approval.
12. **Never write AWS credentials into the repository**, into a skill file,
    into a session log, or into a task brief sent to a subagent. Credentials
    for this project arrive in `.env`, which is gitignored. Never `cat` the
    `.env`, never echo a key, never paste one into an artifact. Load it into
    the environment only (`set -a; . ./.env; set +a`) and verify with
    `aws sts get-caller-identity`, whose output is safe to show.

### Inherited Non-Negotiable Rules

From `sia/guides/questioning-and-approval.md`, restated so they bind here:

1. Never assume on a non-trivial decision.
2. Never delete, replace, or restructure anything on your own initiative —
   present an impact statement naming the concrete consequence, then wait.
3. Never declare a stage done until its acceptance criteria are met *and*
   the user has approved any high-impact work within it.
4. Surface creative/design decisions as options with trade-offs; narrow the
   decision space, do not make the final call alone.

**Severity threshold for this project:** standard. Low proceeds silently;
Medium is flagged and batched; High always blocks on explicit approval.
Anything that creates, mutates, or destroys an AWS resource is High
regardless of size.

## 3. Session Logging

- Path: `_bmad-output/planning-artifacts/sia/logs/sessions/YYYY-MM-DD-session-NN.md`
- **Append as you go.** A session that dies mid-way must still have logged
  everything up to that point. Never buffer a whole session and write at the end.
- Every session-start entry must carry `tool=<exact_harness_name>`
  (e.g. `tool=claude-code`), so a mixed-tool history stays legible.
- Every entry logs usage: token counts where the host exposes them,
  otherwise the fallback proxy — turns, subagent spawns, files touched —
  labelled as a proxy so the two are never confused.
- Every stage outcome is classified **PASS** or **DEVIATION**
  (`sia/capture-interface.md`). Only DEVIATIONs are captured as entries;
  PASSes feed the convergence signal.

**Running-usage ceiling:** **15 subagent spawns** per plan run (user-set
2026-09-15). This host does not expose token counts to the agent, so the
proxy is authoritative: spawns, turns, files touched. Warn explicitly at 80%
(12 spawns); on hitting 15, stop and propose either a scope reduction or a
cheaper model for the remainder, through the approval gate. Log every
ceiling-approach and ceiling-hit via `capture()` with
`error_class: cost-overrun`.

#### AFR-004 — Entity identity must be stable across invocations, not minted per call

**Rule:** Any entity that a creator perceives as persistent — a Folder above
all — must have an identity derived from a stable lookup, never freshly minted
per request. Before creating a Folder record, resolve whether one already
exists for that `(userId, parentFolderId, name)` and reuse its `folderId`.
Writes that create such entities must be read-before-write with a conditional
put, never a blind put. Any test proving a hierarchy invariant must exercise
**at least two separate calls against the same repository**, because
single-call tests are structurally blind to this class of defect.

- **Source event:** F1 adversarial validation,
  `sdd/F1-validation-adversarial-report.md`, defects D1 and D2.
- **Evidence (verbatim):** "Two calls that touch the same folder path mint two
  `randomUUID()` folder records with the same name under the same parent...
  Actual: two folders named `Beats`, each containing one file. The creator's
  library is split in two; `a.wav` is effectively unfindable in the folder they
  later open." And D2: "`C` and `D` end up under *different* `B` folders — a
  genuine mis-parenting, not just duplication."
- **Severity:** high — it silently splits a creator's library and breaks the
  PRD §7 "Add new files" flow, which is the product's headline
  duplicate-handling feature, not an edge case.
- **Error class:** `interface-assumption` — the handler assumed a single-shot
  lifecycle that the product's normal incremental-upload path does not have.
- **Scope:** every handler that creates Folder, Stash, Device or Manifest
  records, and every test asserting a hierarchy or identity invariant.
- **Date introduced:** 2026-09-15
- **Status:** `active`

#### AFR-005 — A quality gate must cover new code structurally, never by enumeration

**Rule:** Any gate that asserts repo-wide quality — typecheck, lint, coverage,
test discovery — must include code by **glob or workspace membership**, never
by an enumerated list of packages. An enumerated gate silently excludes every
package added after it was written, while continuing to exit 0. When adding a
new package, verify the gate actually sees it (e.g.
`tsc -p tsconfig.json --listFiles | grep <newpkg>`) rather than trusting a
green exit code.

- **Source event:** F2 build review, `sdd/task-F2-report.md`; second instance
  of the class first seen as finding F-5 in
  `sdd/F1-validation-rules-review.md`.
- **Evidence (verbatim):** F-5 — "`npx tsc -b` errors `TS5083`. **Nothing in
  the diff is ever type-checked**, while `npm test` is green." Then, after
  F-5 was fixed: "Root `tsconfig.json`'s `include` list enumerates
  `services/handlers/files/**` explicitly and does not cover
  `services/handlers/manifest/**`, so `npm run typecheck` does not currently
  typecheck this package. It exits 0 either way."
  Controller verification: `--listFiles | grep -c handlers/manifest` → `0`.
- **Severity:** medium — no defect shipped, but the gate that exists to catch
  defects was inert for an entire new package while reporting success.
- **Error class:** `unverified-claim` — a green gate accepted as evidence of
  coverage it did not have. **Second occurrence of this class.**
- **Scope:** root `tsconfig.json`, `vitest.config.ts`, any future lint or
  coverage config, and every new workspace package added to this repo.
- **Date introduced:** 2026-09-15
- **Status:** `active`

**Closed out 2026-09-15 (user-directed):** enumeration removed from
`tsconfig.json` entirely. `include` is now `["infra/**/*.ts",
"services/**/*.ts"]`. Verified the way this rule requires — by proof, not by a
green exit code: a probe package at `services/common/src/probe.ts` (a path no
config mentions) with a deliberate type error was caught by `npm run typecheck`
as `error TS2322` with **zero config edits**, then removed and the gate
returned to green.

**Convergence note** (`sia/capture-interface.md`): this class has now recurred.
The F-5 fix addressed the instance, not the class — the replacement gate was
itself written by enumeration. Per the convergence rule this is raised to the
user directly rather than logged a second time, and the F2 fix must make
coverage structural (a glob) rather than adding one more package name.

#### AFR-006 — A conservative guard is only as strong as the query that feeds it

**Rule:** When correctness depends on seeing **all** candidate rows (an
ambiguity check, a uniqueness check, a duplicate check), the query behind it
must be exhaustively paginated before the decision is made. A DynamoDB `Query`
returns at most 1 MB per page; a truncated candidate list silently converts an
"ambiguous → refuse" decision into a confident wrong answer. Never make a
safety decision on the first page of a result set.

- **Source event:** F2 fix validation, `sdd/F2-fix-validation-report.md`,
  Assessment section.
- **Evidence (verbatim):** "pagination of `findByFolderName` [is] untested; a
  user with many same-name folders spanning a 1 MB query page could silently
  truncate the candidate list and turn an ambiguous case back into a `partial`
  — the exact false positive F2-2 exists to prevent."
- **Severity:** high — it would silently re-open a data-loss path that a
  user-ratified decision was created to close, and it would do so only for
  users with large libraries, i.e. exactly the product's target creators.
- **Error class:** `interface-assumption` — the in-memory port returns every
  row, so the guard is correct against the port and wrong against the real
  store it stands in for.
- **Scope:** every DynamoDB `Query` whose completeness a correctness decision
  depends on — `findByFolderName` first, plus `listChildren` (which has no
  pagination at all) and any future uniqueness or duplicate check.
- **Date introduced:** 2026-09-15
- **Status:** `active`

#### AFR-007 — One shared application role is a user-directed deviation from least privilege

**Rule:** This project uses a **single shared execution role** for all Lambda
handlers, by direct user instruction on 2026-09-15. This overrides the approved
spec §3.5 and `skills/stash-aws`, both of which require one role per handler.
Because the blast radius is no longer bounded by per-handler scoping, the role
must instead be bounded by **resource scoping**: no `Resource: "*"` on any
statement, S3 limited to the `users/*` prefix of the one bucket, DynamoDB
limited to the one table and its indexes, logs limited to this app's log-group
prefix. Any future handler needing a genuinely broader permission gets its own
role rather than widening this one.

- **Source event:** User instruction, 2026-09-15 — "we must create a role with
  all the necesary permissions for this application and use the same role for
  the app across".
- **Evidence:** the spec it overrides reads "One execution role per handler. No
  shared 'lambda-role'." (`skills/stash-aws/SKILL.md`), and spec §3.5 requires
  per-handler least privilege.
- **Severity:** high — it widens the blast radius of any single handler bug.
  The read-only `checkManifest` handler now inherits write permissions it has
  no use for, so a defect there could write or delete data it should never
  reach.
- **Error class:** `framework-default-override` — a deliberate, recorded
  override, not a mistake.
- **Scope:** all Lambda execution roles in this project.
- **Date introduced:** 2026-09-15
- **Status:** `active`

**Revisit trigger:** before the private beta takes real creator data, or as
soon as a handler needs a permission the others do not. Splitting back into
per-handler roles is cheap while there are five handlers and expensive later.

#### AFR-002 — A brief must not specify a tool's config exhaustively without verifying that tool's real exit semantics

**Rule:** When a task brief pins a tool's configuration key-by-key *and* also
asserts an expected exit code, verify the tool's actual behaviour first. An
exhaustive config block plus an unverified exit expectation forces the
executor to choose between two instructions that cannot both be satisfied.

- **Source event:** Task 1 report, `sdd/task-1-report.md`, Deviation 2.
- **Evidence (verbatim):** "Step 5 expected `npx vitest run` to exit 0 with
  zero tests. Vitest 2 exits 1 on 'No test files found' unless
  `test.passWithNoTests: true` is set, and the brief specified the config's
  three keys exhaustively without it. I did not add it rather than improvise
  past a spec conflict."
- **Severity:** medium — it cost a round trip and left `npm test` red until
  the first real test lands.
- **Error class:** `interface-assumption`
- **Scope:** every task brief that specifies both a tool config and an
  expected command exit code. Applies to Tasks 2–15 of the current plan.
- **Date introduced:** 2026-09-15
- **Status:** `active`

## 7. Execution Evidence Gate

Execution evidence location: `_bmad-output/implementation-artifacts/sdd/`.

Every implementation task requires, as files, all five of:

1. a **task brief**;
2. a **host-dispatch record**;
3. a **subagent report**;
4. a **reviewer verdict**;
5. a **progress-log entry**.

**This host (Claude Code) supports subagents, so the controller must not
implement a task-owned file itself.** The controller briefs, dispatches,
reviews, integrates and escalates. A controller-written task file is a
DEVIATION with error class `framework-default-override`, not a shortcut.

After every task is individually reviewed and complete, run one
**Integration phase** before the plan is called done: run the full
test/build suite (not each task's own check alone), verify the named
Interfaces between tasks actually match in the combined code, and review
the whole plan's combined diff as one unit. A missing skill manifest or a
missing execution-gate artifact is a DEVIATION, not documentation debt.
