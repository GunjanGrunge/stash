# Isolated React frontend foundation and Tauri distribution migration

Task 1.1 adds a separate React/Vite frontend package with exact direct dependency pins, strict TypeScript settings, and a production build under `ui/dist`. The Vite build, Rust package check, and existing legacy Node contract tests pass, and the Tauri config keeps the existing CSP, window, and capability settings while pointing `frontendDist` at the generated output. The new React source has no native, network, credential, or payload access, and its placeholder text honestly states that authentication migration is deferred. However, that placeholder is now the configured runtime entry, so the launched Tauri app no longer contains the Rust-owned Welcome/sign-in/session flow that the preserved legacy files and tests still exercise.

Watch for: **confirmed** runtime auth/session loss after the `frontendDist` switch; **confirmed** missing frontend `test` script despite the plan's deterministic test command; **likely** clean-checkout launch failure because ignored `dist/` has no build hook; **likely** a broad source-scan exclusion that can hide future code under any `dist` or `node_modules` directory.

**Verdict**: NEEDS_CHANGES

## High-level view

The package boundary is clean: React renders a minimal local component and does not import Tauri or browser networking APIs. Exact direct dependency pins and the lockfile make installation reproducible, while `npm run typecheck` and `npm run build` currently provide the only working frontend validation commands.

The Tauri topology now serves the generated React distribution rather than the legacy static root. The path and unchanged security configuration are compatible, but the generated app is only a placeholder; because the legacy auth implementation is outside the Vite `src` root, the **confirmed** current runtime does not preserve the existing sign-in or remembered-session behavior.

The legacy contracts remain useful for the files they inspect, but they are not an assertion about the new Tauri entry. Their recursive scan was widened to skip generated/dependency directories, and the **confirmed** package has no test runner command yet, leaving the new entry and the **likely** scan boundary without equivalent automated coverage.

<summary>Details</summary>

### React boundary and dependency reproducibility

`ui/src/main.tsx` and `ui/src/app/App.tsx` contain only the React entry and local placeholder rendering. There is no `invoke`, browser networking API, credential/token handling, object-key/presigned-URL handling, filesystem access, or mount access in the new source, which preserves the planned shared-UI boundary. `package.json` pins all seven direct packages exactly, and `package-lock.json` records the resolved dependency graph; the isolated `typecheck` and production build both pass.

The package does not expose the plan's frontend test command: `npm --prefix desktop/apps/stash-desktop/ui run test -- --run` exits 1 with `Missing script: "test"`. This is **confirmed** against the current manifest. The current acceptance brief only lists typecheck/build, but the approved plan also requires a deterministic test/build script and names `run test -- --run` in the frontend validation section. Add that command and its tests, or record a deliberate scope correction rather than reporting a complete foundation validation surface.

### `frontendDist` now selects a placeholder instead of the live auth entry

The relative path `../ui/dist` is accepted by `cargo check`, and the unchanged CSP, undecorated resizable window, and existing capability allowlist remain intact. Vite emits `dist/index.html` and a bundled asset from `ui/src/index.html`, so the configured path is internally consistent after a frontend build.

The behavioral migration is not equivalent to preserving auth. The generated `dist/index.html` loads `src/main.tsx`, whose `App` renders only “React frontend foundation is ready” and a Task 1.2 handoff. The Rust-owned `restore_session`, `sign_in`, `complete_new_password`, and sign-out wiring remains in `ui/index.html`, `ui/welcome.js`, and `ui/post-signin.js`, which are outside the Vite `src` root and therefore absent from `dist`. This is **confirmed** by the source and generated entry. A Tauri launch using the new `frontendDist` cannot sign in or restore a session until the next task lands.

The placeholder copy is honest about that handoff, but honesty does not make the runtime regression safe. Either keep the legacy entry as the configured frontend until the React auth migration is complete, or make the transitional React output retain the existing Rust IPC behavior; in either case, add a smoke/contract assertion against `dist/index.html` so the file Tauri actually loads is covered.

### Clean-checkout build and launch path

`ui/.gitignore` excludes `dist/`, and the repository has no tracked generated frontend output. `tauri.conf.json` has no `beforeDevCommand`, `beforeBuildCommand`, or `devUrl`; the documented README launch command is only `cargo tauri dev --config desktop/apps/stash-desktop/src-tauri/tauri.conf.json`. This makes a clean checkout dependent on an unmentioned prior `npm run build`, and the current `cargo check` does not validate that a frontend directory exists or can be served. This is **likely** to make the documented first launch fail or serve no app when `dist` is absent. Add and verify a Tauri build hook, or update the launch workflow and CI to build the package before any Tauri command.

### Legacy contract coverage after the scanner change

The existing Welcome and post-sign-in suites still pass 20 tests and retain their auth, IPC, CSP, secret, and hierarchy assertions for the legacy static files. Excluding `node_modules` and `dist` avoids scanning third-party/generated text, but the implementation excludes those names at every recursive level of the desktop app. That is **likely** to weaken the intended boundary: a future source directory with either name could contain a browser network call or secret reference and be invisible to the scan. Use path-aware exclusions for `ui/node_modules` and `ui/dist` (plus the existing Rust-generated directories) rather than a name-only global filter.

The no-network/native scan itself finds no violation in the new React source, and the CSP/window/capability settings are unchanged. Those are preserved strengths, not blockers; the missing coverage is that the configured generated entry is a placeholder and is not exercised by the legacy tests.
