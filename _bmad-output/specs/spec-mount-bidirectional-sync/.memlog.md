---
topic: Bidirectional sync between the mounted STASH drive (WinFsp) and the standalone desktop app
updated: 2026-09-18T11:53
---

- (direction) User wants the mounted S: drive and the standalone app to be two views of the same data, Dropbox-style: create folders/files from either side, drag-and-drop, Save-As targeting the mount, full hierarchy preserved, both sides reflect the same state.
- (capability) CAP-1 Folder creation: a folder created in the mounted drive or the app appears, with the same name and position, on the other side.
- (capability) CAP-2 File add via mount: dragging a file of any type into the mounted drive (or Save As from another app) ingests it through the same checksum -> multipart-upload -> verified-commit pipeline as + Stash it, and it appears in the app once committed.
- (capability) CAP-3 File/folder add via app: a Stash completed through the app's existing + Stash it flow appears at the matching path in the mounted drive without requiring a remount.
- (capability) CAP-4 Rename and delete: renaming or deleting a file or folder from either side propagates to the other side, subject to the same identity and verified-commit rules as create.
- (capability) CAP-5 Conflict safety: concurrent writes to the same path from the mount and the app never silently overwrite each other; the loser of a race is surfaced as a conflict, never silently dropped or merged.
- (constraint) A mount-originated write is not reported as present/committed until the same server-verified-commit step + Stash it already requires (AGENT.md rule 4); the local filesystem write completing must not itself imply Stashed.
- (constraint) No write may overwrite an existing S3 key, from either side (AGENT.md rule 8, S3 versioning off); every mount-originated create or re-save mints a new file_id/key rather than reusing one.
- (constraint) Folder creation from the mount reuses the existing read-before-write, conditional-put folder identity resolution (AFR-004: resolve by userId+parentFolderId+name before minting), never a blind create.
- (constraint) Mount-originated uploads go direct-to-S3 via the same presigned multipart path as + Stash it (AGENT.md rule 9); payload bytes must not be routed through Lambda/API Gateway just because the trigger was a filesystem write.
- (constraint) user_id for every mount-originated operation comes from the same verified JWT session the app already holds (AGENT.md rule 7); the mount must not open a separate credential/identity path.
- (constraint) Original file and folder names/paths are preserved verbatim on ingestion from the mount, with no renaming, flattening, or reorganization (AGENT.md rule 1).
- (non-goal) Real-time, sub-second passthrough sync is not required; eventual consistency with a bounded, visible in-progress state (Preparing/Stashing/Verifying, matching + Stash it's existing status vocabulary) is acceptable.
- (non-goal) In-place edit-and-resave of an existing Stash's payload is out of scope; because a Stash is an ingestion event (AGENT.md rule 2) and S3 versioning is off (rule 8), any re-save of a mounted file becomes a new Stash, not a mutation of the old one.
- (non-goal) Multi-device concurrent mounts (the same account mounted from two machines at once) are out of scope for this spec; only one authenticated device's mount plus its own app instance is covered.
- (non-goal) Full POSIX filesystem semantics (permissions, symlinks, extended attributes, hard links) are out of scope; only create, read, rename, and delete of files and folders are covered.
- (note) Success signal: from Explorer on the mounted S: drive, a user creates a folder and drags in a file of any type; within a bounded time the app's Files view shows that exact folder/file at the same path, verified-committed in S3/DynamoDB; conversely a Stash completed in the app appears at the correct mount path without a remount.
- (assumption) Assumed the existing + Stash it checksum/multipart-upload/verified-commit pipeline (desktop/apps/stash-desktop/src-tauri/src/upload.rs) is reused as-is for mount-originated writes, not reimplemented, since it already satisfies rules 4/8/9.
- (assumption) Assumed rollout is staged rather than big-bang, given the mount today (desktop/crates/stash-windows-fs) is an explicitly-scoped read-only flat-root spike with no subdirectories or write callbacks implemented.
- (question) What is the acceptable latency between a mount-side write starting and it becoming visible/committed (seconds vs. tens of seconds), given checksum + multipart upload takes real time for large files?
- (question) When the mount and the app write to the same path at the same time (CAP-5), what should the losing side see: a Windows sharing-violation error at write time, or a later Needs attention/conflict state surfaced after the fact?
- (question) Should a file deleted from the mount move the underlying Stash to Trash (reusing the existing 30-day-retention trash lifecycle) or does mount-delete need its own semantics?
- (question) Does Explorer's Save As dialog need the mount to expose writable-looking folders before any file exists in them (i.e. can empty folders be created ahead of any Stash), or is folder creation always a side effect of the first file landing in it?
- (event) Self-validate pass 1 (coherence): PASS. All 5 capabilities have intent+success, constraints each rule something out, 4 non-goals present, success signal is demonstrable, CAP IDs unique.
- (event) Self-validate pass 2 (preservation): PASS. Every load-bearing claim from the user's direction (folders, any-file-type drag-drop, Save As, subfolder hierarchy, bidirectional create) landed in SPEC.md or write-path-design.md; no wrapper-only drops.
- (event) Spec finalized: SPEC.md + write-path-design.md written to _bmad-output/specs/spec-mount-bidirectional-sync/.
- (decision) Latency: no artificial cap. Small files commit near-instantly; large files show a visible Stashing/Verifying progress state for as long as the real checksum+multipart upload takes, same as + Stash it today. Resolves open question 1.
- (decision) Conflict UX (CAP-5): the losing side of a same-path concurrent write gets an immediate native Windows sharing-violation error at write time, not a deferred Needs attention state. Resolves open question 2.
- (decision) Mount-originated delete (CAP-4) routes through the existing 30-day-retention Trash/restore API — same lifecycle as app-side delete, no separate mount-only delete semantics. Resolves open question 3.
- (decision) Folders can exist empty in the mount (CAP-1 stands on its own, not just as a side effect of a file landing) — needed for Save As to target a freshly created empty folder. Resolves open question 4.
