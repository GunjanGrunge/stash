- (decision) AD-1 [ADOPTED]: Use a Rust core service plus a Tauri v2 UI shell. The service owns filesystem callbacks, synchronization, cache, transfer state, S3 access, and local search; Tauri owns user interaction and must not run filesystem callbacks.
- (decision) AD-2 [ADOPTED]: The Windows mount adapter uses WinFsp through the GPLv3-compatible winfsp Rust crate. STASH is open source and GPLv3-compatible; release work must retain required notices and validate distribution obligations.
- (decision) AD-3 [ADOPTED]: Creative-tool compatibility is an acceptance contract. Cloud-only file opens require bounded latency, byte-range random reads/seeks, efficient directory enumeration/stat, local cache/read-ahead, and bounded fail-fast behavior during network loss.
- (constraint) The existing backend does not expose a client download/range-read authorization endpoint. The mounted-drive spike cannot open cloud payloads until a caller-scoped short-lived download authorization contract is added without exposing object keys or long-lived AWS credentials.
- (event) Initial architecture spine drafted from adopted Windows-first, Rust/Tauri, GPLv3-compatible WinFsp, and creative-tool filesystem decisions. It is draft pending the feasibility-spike implementation plan.
- (decision) AD-3 clarification [ADOPTED]: STASH targets normal Windows mounted-drive semantics, not vendor-specific integrations. Explorer and any available standards-compliant creative application are compatibility evidence only; no named tool is a product dependency.
